# ソース構造と責務

## 構造リファクタリングの範囲

この段階では、オリジナルVer1.5のHTMLに含まれていた<style>の内容をCSSへ、最後のインライン<script>の本文を機能別JSへ**内容を変更せず移動**した。従来の単一ファイル版は比較基準として残す。

- `index.html` はDOM構造と静的リソースの読み込みに専念する。
- `src/js/` は元コードでの宣言順・副作用順に番号を付けて同期読み込みする。
- Three.jsは従来どおりCDNで読み込み、`01-block-registry.js` より前に評価する。
- `08-game-loop.js` の初期ワールドメッシュ生成までに、地形、Mob照明、流体メッシュ関数を定義する。
- `09-inventory.js` と `11-settings.js` は前段階の関数定義とDOMを利用して後から初期化する。

## 現在の責務と結合点

| 層 | 主な状態 | 依存/変更契約の未整理箇所 |
| --- | --- | --- |
| Block registry | BT, NMS, PL, ITEMS | IDと状態ビットの境界 |
| World | C, edits, blockLightDirty, mesh | setB/applyChanges/explode等による更新処理の重複 |
| Entities | mobs, droppedItems, blockLightCache | ワールドと描画の密結合 |
| Circuits | RS, DL, EM, chests | ブロック更新・コンテナ破壊・照明失効 |
| Fluids | FQ, FAC | ブロック変化からのキュー登録 |
| UI/input | hot, invCount, equipped, P | ポーズ・入力受付条件と状態の混在 |
| Persistence | localStorage | セーブ対象の不足と移行バージョン |
| Presentation | scene, mesh, renderer, texture atlas | 状態の変化と再描画の連動 |

## 次の段階で定義する不変条件（現時点では未実装）

1. **ブロックIDと状態**を混同せず、型/エンコード境界を一箇所に集約する。
2. **ワールド変更API**を通るあらゆる更新が、編集履歴、回路登録、流体キュー、照明失効、隣接チャンクのメッシュ更新、コンテナのライフサイクルを整合させる。
3. **シミュレーション状態**（開始/ポーズ/インベントリ）とフレーム更新、入力処理の関係を統一する。
4. **保存データのスキーマ**と旧データからの移行を明文化する。
5. **描画のバッチ化・パフォーマンス改善**は、状態整合性のテストを作ってから実施する。

## パリティ検証の意味

`tests/source-parity.test.mjs` は同一コードが同一順番で配置されたか確認するためのもので、異なるHTMLスクリプト間のグローバル変数共有、WebGL、ユーザー操作、セーブ挙動は静的検査の対象外である。機能修正は別コミットで行う。

## Issue #10: プレイヤー関連処理の分割

1つの大きな `04-player-ui.js` を、状態と保存・入力・コンテナUI・ドロップ物の4ファイルに分けた。従来のコードの**評価順と内容は変更せず**、同じ順序で読み込む。

これは責務の分離の最初の段階。Worldの状態変更APIやRendererの依存解消、既存グローバル状態の完全なカプセル化は引き続き課題である。
